## 할 일별 결과

### 1. CIMD grant 해석 완화 — `apps/oauth/cimd.py`, `apps/oauth/apps.py`

**결정: `_resolve_grant_type` 을 감싼다**(`IGNORED_GRANT_TYPES` 확장 아님).

- 무시 목록을 넓히는 방식은 클라이언트가 **앞으로 더할 grant 이름을 미리 알아야** 한다. Anthropic 이 내일 `token-exchange` 를 더하면 또 깨진다. 감싸는 방식은 「DOT `GRANT_TYPE_MAP` 에 있는 것만 센다」 이므로 이름을 몰라도 된다 — 브리프가 말한 「버전 상승에 덜 취약한 쪽」.
- 새 규칙: `supported = [g for g in grant_types if g in GRANT_TYPE_MAP]` 가 정확히 1개면 원래 함수에 그 하나만 넘긴다(매핑은 여전히 DOT 가 한다). 0개·2개면 `CIMDError`. 무시한 grant 는 INFO 로그.
- `GRANT_TYPE_MAP` 은 `authorization_code`·`implicit` 이다. implicit 은 허브가 RFC 9700 설정으로 이미 막는다(H-3) — 이 완화가 implicit 을 여는 일은 없다. `["authorization_code", "implicit"]` 은 지원 2개로 거부된다(테스트).
- **기동 시 자체 검사**(`OAuthConfig.ready` → `install()`): ① `_build_application_kwargs` 가 여전히 `_resolve_grant_type` 을 모듈 전역으로 부르는지(`co_names`), ② `GRANT_TYPE_MAP`·`IGNORED_GRANT_TYPES`·`CIMDError` 가 있는지 확인하고 감싼 뒤, ③ **claude.ai 표본 문서를 실제로 `_build_application_kwargs` 에 넣어 `authorization-code` 가 나오는지** 본다. 셋 중 하나라도 어긋나면 `WARNING CIMD grant 완화 패치를 적용하지 못했다 …` 를 남기고 기동은 계속한다(CIMD 한 경로의 문제로 서비스 전체를 막지 않는다). 두 번 불러도 겹쳐 감싸지 않는다. 자체 검사 중에는 「무시한 grant」 INFO 를 끈다(기동마다 찍히는 소음 제거 — 라이브에서 확인).
- DOT 가 upstream 에서 같은 완화를 넣으면 ③ 이 그대로 통과하므로 패치는 무해하게 남는다. 그때 걷으면 된다.

테스트(`tests/test_oauth_cimd.py`): 패치 적용·멱등 · claude.ai 3종 → `authorization-code` · 지원 0개(`refresh_token`+`jwt-bearer`, `client_credentials`)·2개(`authorization_code`+`implicit`) → 여전히 `CIMDError` · `resolve_cimd_application` 이 공개 Application 을 만든다(fetcher 만 가짜).

### 2. 오류 오표시 수정 — `apps/oauth/views.py`, `templates/oauth2_provider/authorize.html`

- `ToolboxAuthorizationView.get` 의 분기를 셋으로 나눴다: 리디렉트(컨텍스트 없음) → 그대로 · **`error` 컨텍스트 → DOT 오류 화면 그대로** · 검증 성공인데 `scopes` 가 빔(= 도구함과의 교집합 없음) → 빈 도구함 화면. 전에는 둘째가 셋째로 빨려 들어가 「도구함이 비어 있습니다」 가 떴다.
- CIMD 해석이 실패하면 DOT 는 그 클라이언트를 모르는 것으로 처리하고(`resolve_cimd_application` → `None`) oauthlib 가 `InvalidClientIdError`(`invalid_request` / `Invalid client_id parameter value.`)를 낸다. 원인 문자열은 DOT 안에서 로그로만 나가고 뷰까지 오지 않는다. 그래서 뷰는 **오류가 `InvalidClientIdError` 이고 client_id 가 CIMD URL 일 때** `cimd_client_id`·`cimd_retry_seconds`(= `CIMD_FAILURE_BACKOFF_SECONDS`, 60) 를 컨텍스트에 더하고, 템플릿이 다음을 보여 준다:
  > 연결할 수 없습니다 · 클라이언트 등록(CIMD) 실패: 연결을 요청한 앱의 등록 정보(`<URL>`)를 받아오지 못했거나, 허브가 받아들일 수 없는 내용이었습니다. 잠시 뒤(60초 이상) Claude 에서 연결을 다시 시도하세요. 계속 실패하면 허브 운영자에게 알려 주세요 — 원인은 서버 로그에 남아 있습니다. (`invalid_request` Invalid client_id parameter value.)
- 그 밖의 오류(예: 등록되지 않은 콜백)는 기존 「연결할 수 없습니다 + 오류 코드·설명」 에 「Claude 에서 연결을 처음부터 다시 시도하세요」 한 줄을 더했다.
- 새 Tailwind 클래스는 없다(`just css` 뒤 `static/css/hub.css` 변경 0).

테스트: CIMD 실패 → 400 + 「클라이언트 등록(CIMD) 실패」, 빈 도구함 문구·폼 없음 · 일반 오류(잘못된 콜백) → 오류 화면, CIMD 문구 없음 · 검증 통과 + 교집합 없음 → 빈 도구함 · 정상 → 동의 폼(스코프 `tool:kosis`·`tool:weather`).

### 3. CIMD 실패 로그

- 원래도 DOT 가 `INFO CIMD resolution failed for '<client_id URL>': CIMDError(...)` 를 남긴다(운영 `DJANGO_LOG_LEVEL` 기본 INFO — 운영 로그에 보였던 그 줄). **URL 은 이미 남고, grant 목록은 없었다.**
- 완화판의 오류 메시지에 문서의 `grant_types` 전체와 지원 목록을 싣는다: `client metadata must declare exactly one supported grant type (supported: ['authorization_code', 'implicit']); got grant_types=[...]`. 테스트가 로그에 URL·grant 목록이 둘 다 있는지 확인한다.
- 성공 경로에서 무시한 grant 는 `INFO CIMD: 지원하지 않는 grant 를 무시한다 [...] (grant_types=[...])` — 다음에 claude.ai 가 문서를 바꿀 때 로그만 보고 알 수 있다.

## upstream(DOT) 이슈/PR 초안 — 게시는 사용자 결정

**제목**: CIMD/DCR: ignore unsupported `grant_types` instead of rejecting client metadata (claude.ai now lists `jwt-bearer`)

**본문**:

> Since mid-September 2026, claude.ai's Client ID Metadata Document (`https://claude.ai/oauth/mcp-oauth-client-metadata`) declares
>
> ```json
> "grant_types": ["authorization_code", "refresh_token", "urn:ietf:params:oauth:grant-type:jwt-bearer"]
> ```
>
> With `CIMD_ENABLED = True` (3.4.1), resolution fails with `CIMDError('client metadata must declare exactly one non-refresh grant type')`, the authorization request falls through to `invalid_client_id`, and Claude custom connectors can no longer connect to any DOT-based MCP authorization server.
>
> **Reproduce**: serve a CIMD document with the three grant types above (or point `client_id` at the claude.ai URL with `CIMD_ALLOWED_HOSTS = ["claude.ai"]`) and GET `/o/authorize/?client_id=<url>&response_type=code&…`.
>
> **Why relax**: RFC 7591 §2 describes `grant_types` as the grant types the client *may* use; the AS is free to register a subset. `_resolve_grant_type` already skips `refresh_token` for the same reason. Counting only grants the AS can map (`GRANT_TYPE_MAP`) keeps the "one DOT grant per Application" constraint while tolerating clients that advertise extra capabilities. Clients that declare zero or several *supported* grants are still rejected.
>
> **Proposed diff** (`oauth2_provider/cimd.py`; `views/dynamic_client_registration.py::_resolve_grant_type` has the same shape and would need the same change):
>
> ```diff
>  def _resolve_grant_type(grant_types):
>      """Resolve an RFC 7591 grant_types list to a single DOT grant constant."""
> -    meaningful = [g for g in grant_types if g not in IGNORED_GRANT_TYPES]
> -    if len(meaningful) != 1:
> -        raise CIMDError("client metadata must declare exactly one non-refresh grant type")
> -    grant = GRANT_TYPE_MAP.get(meaningful[0])
> -    if grant is None:
> -        raise CIMDError(f"unsupported grant_type: {meaningful[0]!r}")
> -    return grant
> +    # RFC 7591 §2: grant_types lists what the client may use; ignore what we don't support.
> +    supported = [g for g in grant_types if g in GRANT_TYPE_MAP]
> +    if len(supported) != 1:
> +        raise CIMDError(
> +            "client metadata must declare exactly one supported grant type "
> +            f"(supported: {sorted(GRANT_TYPE_MAP)}); got grant_types={list(grant_types)!r}"
> +        )
> +    return GRANT_TYPE_MAP[supported[0]]
> ```
>
> Tests: the claude.ai document resolves to `authorization-code`; `["refresh_token", "urn:…:jwt-bearer"]`, `["client_credentials"]` and `["authorization_code", "implicit"]` still raise. Happy to open a PR.

## 남은 질문·관찰

- **DCR 폴백도 같은 규칙**(`views/dynamic_client_registration.py::_resolve_grant_type`)이다. claude.ai 는 CIMD 를 먼저 쓰므로 이번 장애와 무관하지만, 어떤 클라이언트가 DCR 요청에 `jwt-bearer` 를 넣으면 `invalid_client_metadata` 로 떨어진다. 이번 핫픽스 범위(CIMD) 밖이라 손대지 않았다 — 필요하면 같은 방식으로 감쌀 수 있다(DCR 은 오류를 응답 튜플로 돌려주므로 감싸는 코드 모양만 다르다).
- **운영의 60초 백오프**: 배포 직전 실패한 claude.ai URL 은 캐시에 60초 백오프가 걸려 있을 수 있다. 배포 직후 1분 안의 재시도가 여전히 오류 화면이면 1분 뒤 다시 — 새 오류 화면이 그렇게 안내한다.
- 운영 배포 후 공개 HTTPS 에서의 OAuth 왕복 실측(커스텀 커넥터 축의 정본)은 오케스트레이터가 `v0.3.1` 배포 뒤 할 일이다.
