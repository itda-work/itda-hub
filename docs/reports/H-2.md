## Django 6.1 에서 고친 것

**코드 수정이 필요한 폐기·비호환은 없었다.** 확인한 것:

- `manage.py check --fail-level WARNING` 0건, `makemigrations --check` 변경 없음(마이그레이션 헤더의 "Generated by Django 5.2.17" 은 그대로 둔다 — 재생성하지 않음).
- 테스트 전체와 `manage.py check` 를 `-W error::DeprecationWarning -W error::PendingDeprecationWarning` 으로 — Django `RemovedInDjango70Warning`(Pending) 포함 0건.
- SQLite `OPTIONS`(`transaction_mode='IMMEDIATE'`·`init_command`·`timeout`), `STORAGES`, allauth 설정(`ACCOUNT_LOGIN_METHODS`·`ACCOUNT_SIGNUP_FIELDS`·`SOCIALACCOUNT_ONLY`), DOT 설정 키 전부 6.1 에서 그대로 유효. allauth·DOT 버전이 바뀌지 않아 설정 변경 없음.
- 드러난 경고 하나(폐기 아님): whitenoise 의 `UserWarning: No directory at …/staticfiles/` — 테스트가 collectstatic 없이 돌아서다. pytest `filterwarnings` 에서 그 메시지만 끈다(운영 이미지는 굽는다).
- 새 테스트를 쓰다 만난 것: starlette `TestClient` 가 anyio 의 폐기 별칭(`anyio.abc.BlockingPortal`)을 건드린다 → mcp healthz 테스트는 `httpx.ASGITransport` 로 잰다.

## 운영 준비 — 무엇을 확인했나

### 프록시(Caddy) 뒤 동작

`tests/test_production_settings.py`(새 프로세스, `HUB_BASE_URL=https://hub.itda.work`):

- `SECURE_PROXY_SSL_HEADER=('HTTP_X_FORWARDED_PROTO','https')`, 세션·CSRF 쿠키 Secure, CSRF 오리진 = `https://hub.itda.work`.
- `X-Forwarded-Proto: https` 가 붙은 요청만 `is_secure()` 이고 절대 주소가 `https://hub.itda.work/…` — 헤더 없는 직접 요청은 https 가 아니다.
- RFC 8414 `issuer` == `HUB_BASE_URL`, `authorization_endpoint`·`token_endpoint` 가 https, RFC 9728 `resource` == `HUB_MCP_URL`.
- 음성 대조: 설정에서 `SECURE_PROXY_SSL_HEADER` 를 빼면 위 테스트가 실패하는 것을 확인했다(원복함).
- `USE_X_FORWARDED_HOST` 는 켜지 않았다 — Caddy 는 `Host` 를 그대로 넘기므로 필요 없고, 켜면 신뢰 범위만 넓어진다.

라이브(실제 gunicorn 26 뒤): 운영 이미지로 https 설정의 web 을 띄우고 **다른 컨테이너**(hub-mcp)에서 `Host: hub.itda.work` + `X-Forwarded-Proto: https` 로 요청 → `issuer` = `https://hub.itda.work`, CSRF 쿠키 Secure, `/accounts/google/login/` POST 가 CSRF Origin 검사를 통과해 302, `redirect_uri=https://hub.itda.work/accounts/google/login/callback/`. gunicorn 이 비신뢰 IP 에서 온 `X-Forwarded-Proto` 를 떨구지 않고 Django 까지 넘기는 것을 실측으로 확인했다.

### Google 로그인

- 자격이 있으면 `allauth.socialaccount.providers.google` 이 설치되고 `reverse('google_callback') == '/accounts/google/login/callback/'` — 테스트로 고정.
- `GOOGLE_OAUTH_CLIENT_ID` 더미로 띄운 컨테이너의 `/accounts/login/` 에 `<a title="Google" href="/accounts/google/login/?process=login">Google</a>` 가 비밀번호 폼과 함께 나온다(`HUB_LOCAL_LOGIN=1` 병행).

### 운영 오버레이와 백업

- `docker compose -f compose.yml -f compose.prod.yml up -d --build` → 두 컨테이너 healthy, **호스트 포트 없음**. `.env` 에 `WEB_CONCURRENCY` 가 없으면 1(`config` 로 확인), 있으면 그 값.
- 오버레이 상태에서 서비스 이름 경로로 스모크(`hub-web` 안에서 `HUB_MCP_URL=http://hub-mcp:8080/mcp`) 통과 — Caddy 가 갈 경로와 같다.
- `just backup`(`--profile ops run --rm hub-backup`) → `hub-20260920-001052.sqlite3`(410 KB), 호스트에서 `integrity_check` ok, 토큰·궤적 행이 들어 있음.
- include 방식: 임시 디렉터리에 `web` 서비스를 가진 가짜 웹사이트 프로젝트를 두고 `include: - path: [compose.yml, compose.prod.yml]` → `config` 가 `hub-web`·`hub-mcp`·`web` 셋을 충돌 없이 내고, 포트 없음, 빌드 컨텍스트는 허브 디렉터리, 볼륨 이름 `itda-hub_hub-data` 유지.

## 운영 오버레이 사용법(웹사이트 M8-C 용 요약)

정본은 `docs/deploy.md` 「동거 배포」.

1. VM 에 허브 저장소를 체크아웃하고(예 `/opt/itda-hub`) 허브 전용 `.env` 를 둔다(`.env.example` 「운영」 절: `HUB_BASE_URL=https://hub.itda.work` · `HUB_MCP_URL=https://hub.itda.work/mcp` · `DJANGO_ALLOWED_HOSTS=hub.itda.work` · `HUB_LOCAL_LOGIN=1` · Google 자격 · 불변 `HUB_SETTINGS_ENCRYPTION_KEY` · `HUB_BACKUP_DIR`).
2. 웹사이트 `compose.prod.yaml` 에 `include: - path: [/opt/itda-hub/compose.yml, /opt/itda-hub/compose.prod.yml]`.
3. `Caddyfile.prod` 에 `hub.itda.work` 블록 — `/mcp*` → `hub-mcp:8080`(`flush_interval -1`), 나머지 → `hub-web:8000`, 캐시 없음.
4. cron `30 3 * * *` 에 `docker compose -f compose.yaml -f compose.prod.yaml --profile ops run --rm hub-backup`.
5. 검증: 로컬 스모크 → 원격 스모크(발견 문서·`/healthz`·`HUB_MCP_URL=https://hub.itda.work/mcp just smoke`·Google 로그인) → 커스텀 커넥터 OAuth 왕복(#1).

## 남은 질문

1. **`HUB_LOCAL_LOGIN=1` 병행 = 공개 회원가입이 비밀번호로 열린다.** 지금 설정은 로컬 로그인이 켜지면 `ACCOUNT_SIGNUP_FIELDS` 에 비밀번호가 들어가고 `SOCIALACCOUNT_ONLY=False` 라, 운영에서 누구나 이메일+비밀번호로 가입할 수 있다(이메일 검증 없음). "비상용 관리자 로그인" 의도라면 Google 이 켜졌을 때 로컬 **가입**만 막는 설정(allauth `ACCOUNT_ADAPTER.is_open_for_signup` 등)이 필요하다. 로그인 흐름 변경이라 이 과업(기능 변경 금지) 밖으로 두었다 — 동거 전에 결정이 필요하다.
2. **`check --deploy` 경고.** `--fail-level WARNING`(기본 태그)은 0건이지만 `--deploy` 에서는 DOT 의 RFC 9700 경고 W001–W005·W007·W008(implicit·password grant 허용, PKCE `plain` 허용, 쿼리스트링 토큰 허용, RFC 9207 `iss` 생략, refresh 재사용 탐지 꺼짐, http redirect 허용 — DOT 4.0 에서 기본값이 바뀐다)과 Django `security.W004`(HSTS)·`W008`(SSL redirect — Caddy 가 맡음)이 난다. 대부분 켜는 것이 맞아 보이지만 OAuth 흐름 변경이라 손대지 않았다. **W008(http redirect 금지)은 켜면 안 된다** — Claude Code 등 네이티브 클라이언트의 `http://127.0.0.1` 루프백 콜백(RFC 8252)이 막힌다. 나머지를 켤지 별도 과업으로.
3. **VM 에서의 이미지 공급.** 오버레이는 `build: .` 을 유지한다(VM 에서 빌드 — Go 컴파일이 없어 1 GiB 에서도 가능하지만, django-itda 가 git 소스라 빌드 단계에 git·GitHub 접근이 필요). 웹사이트처럼 "레지스트리 없는 배포"로 이미지를 옮기려면 `HUB_IMAGE` 로 태그를 주면 된다. 어느 쪽으로 할지.
4. **`/healthz` 공개 여부.** Caddy 블록이 나머지 경로를 전부 web 으로 보내므로 `https://hub.itda.work/healthz` 가 공개된다(내용은 `ok`·`db`·`introspection_app` 불리언뿐). 막으려면 Caddy 에서 `/healthz` 를 내부 전용으로.
5. **CI 는 아직 GitHub 에서 돈 적이 없다**(푸시 금지). actionlint 와 깨끗한 clone 재현만 했다. `extractions/setup-just@v2`·gha 캐시는 첫 푸시에서 확인.
6. hub-mcp healthcheck(10초)가 uvicorn 접근 로그에 한 줄씩 남는다. 로그 회전(10m×5)이 있어 두었지만, 줄이려면 간격을 늘리거나 접근 로그에서 `/healthz` 를 거른다.
7. 로컬 정리: 서비스 이름을 바꿔 옛 이미지 `itda-hub-web:latest`·`itda-hub-mcp:latest`(각 676 MB)가 고아가 됐다. 지우지 않았다. 볼륨 `itda-hub_hub-data` 는 그대로 이어 쓴다(로컬 compose 는 새 이름으로 다시 떠 있음, 127.0.0.1:8100/8180).
