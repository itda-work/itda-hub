## 할 일별 결과

### 1. 로컬 로그인 정책 (H-2 질문 1)

- `settings.HUB_LOCAL_SIGNUP = HUB_LOCAL_LOGIN and not GOOGLE_OAUTH_CLIENT_ID` — 판정 한 곳.
- `apps/accounts/adapters.py`: `AccountAdapter.is_open_for_signup` 이 그 값을 쓴다. **`SocialAccountAdapter.is_open_for_signup` 은 True** — allauth 기본 구현은 계정 어댑터를 따라가서, 로컬 가입만 닫으려 해도 Google 가입까지 같이 닫힌다(음성 대조로 확인).
- `ACCOUNT_SIGNUP_FIELDS`·`SOCIALACCOUNT_ONLY` 는 그대로 — 로그인 폼(비밀번호)은 `HUB_LOCAL_LOGIN` 을 따라 남아야 하므로 어댑터로 가입만 가른다.
- `/accounts/signup/` 은 Google 이 켜지면 allauth 「가입 닫힘」 화면(200, 폼 없음), POST 도 계정을 만들지 않는다. 404 가 아니라 allauth 표준 차단 화면을 택했다 — 404 는 URL 패턴을 걷어내야 해서 allauth 내부 `reverse('account_signup')` 들과 부딪힌다.
- 닫힌 가입으로 가는 링크를 없앴다: allauth 기본 레이아웃의 메뉴는 정책과 무관하게 「Sign Up」을 내므로 `templates/allauth/layouts/base.html` 이 허브 `base.html` 을 쓰게 했고, `templates/account/login.html`(allauth 65 사본, 바꾼 것은 가입 안내 문단을 `HUB_LOCAL_SIGNUP` 으로 감싼 것 하나)과 컨텍스트 프로세서 `apps.accounts.context_processors.signup` 을 두었다. allauth 를 올리면 이 사본을 원본과 대조한다.
- 테스트로 고정:
  - Google 켬 + 로컬 켬(`tests/test_production_settings.py::test_구글이_켜지면_로컬_가입만_닫힌다`, 새 프로세스): 로그인 화면에 가입 링크 없음 · 가입 폼 없음 · 가입 POST 로 계정 안 생김 · **기존 로컬 계정 로그인 302 → 도구함 200** · **Google 가입**(제공자의 `sociallogin_from_response` 로 userinfo 모양의 SocialLogin 을 만들어 `complete_social_login` 을 태움) → 302, `SocialAccount` 생성.
  - Google 끔(`tests/test_local_login.py::test_구글이_꺼져_있으면_로컬_가입이_열린다`): 로그인 화면에 가입 링크 · 가입 POST 302 · 계정 생성.
  - 음성 대조 3종 — `HUB_LOCAL_SIGNUP = HUB_LOCAL_LOGIN` 으로 되돌림 / 계정 어댑터를 기본으로 / 소셜 어댑터를 기본으로 — 각각 해당 단언이 실패하는 것을 확인했다(원복함).

### 3. `/healthz` 노출 (H-2 질문 4)

- 공개는 유지. web 은 `@never_cache`(`Cache-Control: max-age=0, no-cache, no-store, must-revalidate, private`), mcp 는 `Cache-Control: no-store`.
- UA 무관: 테스트가 `Mozilla/5.0`·`Googlebot/2.1`·`curl/8.0`·빈 UA 로 같은 상태 코드·같은 본문을 확인한다(web·mcp 둘 다, 503 응답도 no-store).
- `docs/deploy.md` 에 Caddy 매처 예시 — `@healthz_public { path /healthz; not remote_ip private_ranges }` → `respond 404`, `handle` 맨 위. `caddy:2` 이미지의 `caddy adapt --validate` 로 문법 검증 통과. CDN 을 앞에 두면 `client_ip`·`trusted_proxies` 가 필요하다는 주의와, 기본값은 열어 둔다는 결정을 같이 적었다.

### 4. mcp healthcheck 로그 소음 (H-2 질문 6)

- `mcp_server/logs.py`: uvicorn 기본 `LOGGING_CONFIG` 사본의 access 핸들러에 필터 — **성공(2xx)한 `/healthz` 만** 거르고 503 은 남긴다(헬스가 나빠진 순간은 보여야 한다). `python -m mcp_server` 가 `uvicorn_config={'log_config': …}` 로 넘긴다(fastmcp 4 `run(transport='http', uvicorn_config=…)`). 간격(10초)은 그대로.
- 테스트: 필터 단위(200 거름·503 남김·`/mcp` 남김·`/healthzz` 남김) + 실제 `uvicorn.Config` 의 dictConfig 경로를 태운 뒤 `uvicorn.access` 로거 출력에서 healthz 줄이 사라지는지.
- 라이브: 재빌드 뒤 hub-mcp 로그 40초 창에 `healthz` 0줄, healthcheck 5회 연속 exit 0. `/mcp` 접근 줄(401·200)은 그대로 남는다.

## 발견한 결함 — 동의 스코프 우회 (v0.1.0 부터)

라이브 확인 중 **빈 도구함의 사용자에게 `tool:kosis tool:weather` 토큰이 발급**됐다.

- 원인: `ToolboxAuthorizationView.form_valid` 가 요청 스코프를 도구함과 교집합해 넘기는데, 교집합이 비면 빈 문자열이 DOT 로 가고, DOT/oauthlib 은 빈 스코프를 **기본 스코프** 로 채운다. `CatalogScopes.get_default_scopes` 는 카탈로그 전체다. 그래서 (a) 도구함 밖 스코프만 요청하거나 (b) 빈 도구함인 사용자가 동의 폼을 직접 POST 하면(「도구함이 비어 있습니다」 화면에도 로그아웃 폼의 CSRF 토큰이 있다) 카탈로그 전체 스코프의 토큰이 나왔다. (c) `approval_prompt=auto` 경로는 `token.allow_scopes([])` 가 항상 참이라 이전 토큰이 있으면 동의 화면 없이 같은 결과.
- 영향: 불변식 「토큰 스코프 = 도구함」 붕괴. 도구 실행은 여전히 자격증명(개인 키·공용 키)을 따로 보지만, 공개 도구(날씨)와 공용 키가 설정된 도구는 도구함에 없어도 불릴 수 있었다. 연결 토큰 경로(`apps/toolbox/tokens.py`)는 무관. 아직 공개 배포 전이다.
- 수정: 발급 관문을 `create_authorization_response` 하나로 — 동의 폼 POST·`skip_authorization`·`approval_prompt=auto` 가 모두 지나는 DOT 메서드다. 여기서 다시 좁히고, `allow` 인데 비면 `OAuthToolkitError(AccessDeniedError(state))` → 클라이언트에 `error=access_denied&state=…` 리디렉트, Grant·토큰 없음. `form_valid` 의 좁히기는 관문으로 옮겼다.
- 테스트(`tests/test_oauth_consent.py`, 3개): 도구함 밖 스코프만 요청 → `access_denied`·Grant 0·토큰 0 / 빈 도구함 + 직접 POST → 거부 / `approval_prompt=auto` + 이전 토큰 → 도구함 밖은 코드 없음, 도구함 안은 자동 승인되고 Grant 스코프 = `tool:weather`. 세 테스트 모두 **수정 전 코드에서 실패**하는 것을 먼저 확인했다.
- 라이브 재확인: 운영 이미지에서 빈 도구함 → `access_denied`, 날씨를 담은 뒤 S256 → 토큰 스코프 `tool:weather`(전체를 요청해도).
- `get_default_scopes` 는 바꾸지 않았다 — 스코프 없이 오는 인가 요청(기본 = 전체 → 도구함으로 좁힘)을 그대로 두고, 빈 결과만 관문에서 막는다.

## 라이브 확인 (운영 이미지 · https 설정)

H-2 방식 그대로: 최종 이미지로 `HUB_BASE_URL=https://hub.itda.work`·Google 더미 자격·`HUB_LOCAL_LOGIN=1`·임시 DB 의 web 컨테이너(`hub-probe`, gunicorn)를 compose 네트워크에 띄우고, **hub-mcp 컨테이너 안에서** `Host: hub.itda.work` + `X-Forwarded-Proto: https` 로 두드렸다(끝나고 지움).

| 항목 | 결과 |
|---|---|
| `/healthz` (프록시 헤더) | 200 · `Strict-Transport-Security: max-age=31536000; includeSubDomains` · no-store |
| `/healthz` (내부 `Host: hub-probe`, 헤더 없음) | 200 · HSTS 없음 · 리디렉트 없음 |
| 로그인 화면 | Google 링크 있음 · 비밀번호 폼 있음 · **가입 링크 없음** · CSRF 쿠키 Secure |
| `/accounts/signup/` GET / POST | 200 「가입 닫힘」, 폼 없음 / 200(계정 생성 안 됨 — 단위 테스트가 DB 로 확인) |
| 관리자(bootstrap 계정) 로그인 | 302 → `/toolbox/` → 200 |
| DCR `http://127.0.0.1:33418/callback` / `https://claude.ai/api/mcp/auth_callback` | 400 / 201 |
| 빈 도구함 + 인가 POST | 302 `error=access_denied`, 코드 없음 |
| 도구함(날씨) + S256 인가 | 302 `code`·`state`·`iss=https://hub.itda.work` → 토큰 200 `scope=tool:weather`, Bearer |
| plain 인가 | 302 `error=invalid_request`, 코드 없음 |

로컬 compose(`127.0.0.1:8100/8180`)의 메타데이터: `grant_types_supported` 에 implicit·password 없음, `response_types_supported=["code"]`, `code_challenge_methods_supported=["S256"]`, `authorization_response_iss_parameter_supported: true`.

## 남은 질문

1. **운영에서 http 루프백 콜백 금지의 대가.** Claude Code 가 헤더 없이 `claude mcp add --transport http … https://hub.itda.work/mcp` 로 붙으면 자체 OAuth(DCR + `http://localhost:<포트>/callback`)를 시도하는데, 운영에서는 그 등록이 400 이 된다. 강의 가이드는 연결 토큰(헤더) 방식이라 영향이 없지만, 교육생이 헤더를 빼먹으면 「등록 실패」로 보인다. 필요해지면 DOT 의 `Application.get_allowed_schemes()` 를 루프백 IP(`127.0.0.1`/`[::1]`)에만 http 를 허용하도록 좁혀 여는 방법이 있다(그때 W008 은 조용히 둬야 한다).
2. **HSTS 기본 1년.** 한 번 나가면 브라우저가 1년간 hub.itda.work 를 https 로만 연다(되돌리기 어렵다). Caddy 자동 HTTPS 전제라 문제는 없어 보이지만, 첫 공개 때 `HUB_HSTS_SECONDS=300` 으로 시작해 확인 뒤 올릴지 운영 결정.
3. **Caddy `/healthz` 매처는 문법 검증만.** 공인 IP 에서 404 가 되는지는 공개 배포 뒤 확인 대상(원격 스모크 항목으로 넣어 두었다). 기본값은 열어 둔다.
4. **allauth 템플릿 사본**(`templates/account/login.html`)은 allauth 를 올릴 때 원본과 대조해야 한다. allauth 화면이 이제 허브 레이아웃을 쓰므로 비밀번호 재설정 등 다른 allauth 화면의 모양도 바뀌었다(동작은 그대로 — 전체 테스트 통과).
5. **CI 는 여전히 GitHub 에서 돈 적이 없다**(푸시 금지, H-2 질문 5 그대로).
6. 검증하다 만난 함정(코드 결함 아님, 문서화 후보): `just token` 은 안내 줄을 stderr, 토큰을 stdout 으로 낸다 — `$(just token … 2>&1 | tail -1)` 로 받으면 가끔 안내 줄이 잡혀 스모크가 401 로 실패한다(3할 정도 재현). `2>/dev/null` 로 받으면 된다. 또 `just smoke` 의 기본 주소는 `:8080` 이라 `.env` 에서 포트를 바꾼 로컬은 `HUB_MCP_URL` 을 같이 줘야 한다.
7. 로컬 정리: compose 는 최종 이미지로 다시 떠 있다(`127.0.0.1:8100/8180`). 검증용 `hub-probe` 컨테이너는 지웠다. 검증 중 `caddy:2` 이미지를 받았다.
